How to use MongoDB Data Collector

MongoDB Data Collector copies diagnostic files from a MongoDB cluster so they can be reviewed. It only reads. It does not change your data, settings, or running processes.

Where to run it

Run MongoDB Data Collector on its own computer: a laptop, jump host, or bastion that can reach the cluster. That computer is not a mongod. The collected files are saved there, so the database hosts are not writing the output.

This page is plain HTTP and has no login. Only this computer can open it. Anyone else logged in on this computer can open it too, so do not run it on a machine you share. If your browser is on another computer, use the SSH tunnel in the README (dcr web -via). Do not try to publish this page.

It can run on a mongod host, but avoid that. That host then stores every file you collect and does the copy work. Do not use the primary. A secondary is less harmful, but it is still a database host.

Kubernetes and containers

MongoDB Data Collector connects to MongoDB members by hostname and port. It does not use the Kubernetes API and it does not run kubectl exec. What it can collect depends on which network and files the collector host can reach.

DataTypical Kubernetes resultWhat is required
getMongoData Available Every discovered pod hostname and MongoDB port must be reachable from the collector. Run MongoDB Data Collector inside the cluster network, or provide routable DNS and ports.
MongoDB shell checks Available The same MongoDB network access and user permissions as getMongoData. This includes rs.status() and sh.status().
FTDC and mongod logs Usually unavailable The collector needs SSH and rsync into the container, and most pods do not run SSH. For a Kubernetes deployment managed by Ops Manager, collect FTDC and mongod logs there instead. See View, Retrieve, and Manage Logs.
df and ulimit Limited Remote checks need SSH. Even when available, container disk and limits may not represent the Kubernetes worker node. MongoDB Data Collector does not collect worker-node settings.
Kubernetes metadata Not collected Pod events, manifests, resource requests and limits, PVC details, and operator logs require separate kubectl collection.

Safe choice: select only getMongoData and Commands, and leave the SSH username blank when pods have no SSH service. MongoDB shell checks still run; df and ulimit are skipped without SSH. For FTDC and mongod logs, use Ops Manager. In the deployment, request MongoDB Logs and MongoDB FTDC Data, then download the archive. Details are in the Ops Manager log documentation.

Before you start

Check these before you connect.

On this computer (collector host)

  • mongosh must be installed. The older mongo shell can work, but mongosh is the one to use.
  • Every cluster member must resolve by the same hostname the cluster uses. If a name does not resolve, add it to /etc/hosts.
  • Plan about 1.5 GB free for one MongoDB member, then about 400 MB for each extra member. Three members is about 2.2 GB. The collector stops if free space drops under about 1.1 GB. Logs can be larger.
  • Install rsync on the computer running MongoDB Data Collector. It copies FTDC and logs from MongoDB hosts, which are normally other machines.

To reach the cluster

  • The collector host must open the MongoDB port on every member for the whole run. If one member is down, collection stops.
  • For FTDC, logs, or host checks on a remote machine, you need SSH to it. The SSH user must be able to read the MongoDB files.
  • You type the SSH password once per node, in a box on this page.

MongoDB login

  • If login is off, leave the username and password blank.
  • If login is on, use a user with backup, readAnyDatabase, and clusterMonitor.
  • On a sharded cluster, create that same user on each shard primary. A user only on mongos cannot log in to the shards.
  • On MongoDB 8.0 or newer, also grant directShardOperations on each shard while you collect, then remove it.

The five steps

  1. Connect. Give the collection a name and one host you can already reach. On a sharded cluster, use a mongos when you can. Do not put replicaSet in URI options. MongoDB Data Collector finds the rest of the cluster itself.
  2. Topology. Check the members it found. Hover a node to see its role.
  3. Scope. Pick which nodes and which files. The usual choice is one secondary, so the primary is left alone. Collection runs one node at a time.
  4. Collect. Watch the progress. getMongoData stops after 2,500 collections unless you raise Max collections on the connect form.
  5. Results. Files are saved under ./outputs/<cluster name>/ on the collector host. Zip that folder. If you already have a support case, upload the archive to that case. If you do not, open one from MongoDB Support and attach the files.

What gets copied

These are the files MongoDB Data Collector can collect. Commands are a separate choice and are selected by default.

WhatWhat it is
getMongoData A snapshot of server, database, and index stats.
FTDC The metrics files MongoDB already wrote.
Mongod logs The log files already on the host.
A few commands Disk space, resource limits, and replica-set or shard status.

This page is the short version. For flags, the config file, and the full prerequisite list, see the dcrcli README.

Connect to a seed node

MongoDB Data Collector discovers the rest of the cluster from one reachable mongod or mongos. On a sharded cluster, use a mongos when you can. The terminal UI is still available: run dcrcli without web.

A password is already in memory for this username. Leave the field blank to keep it.

Do not put replicaSet in URI options. MongoDB Data Collector discovers topology itself. mongosh or mongo must be on PATH.

Using Kubernetes or containers?

getMongoData and Commands work when every pod hostname and MongoDB port is reachable. Select both and leave the SSH username blank when pods have no SSH service; MongoDB shell checks run while df and ulimit are skipped.

FTDC and mongod logs: use Ops Manager instead. Request MongoDB Logs and MongoDB FTDC Data, then download the archive. See the Ops Manager log documentation. df and ulimit usually do not work here either, because most pods do not run SSH.

Open How to use for the full capability list.

Commands are df, ulimit, replica-set and shard status, the time-series check, and unique indexes. They are part of the default collection. Uncheck Commands to skip them.

If a node asks for an SSH password or a host-key confirmation, the prompt opens here in the browser. MongoDB Data Collector shares one SSH connection per node, so you answer once per node, like the CLI.
